# Dusty Dragon M66–M75 — Semantic Unification & Controlled Demo Desk

M66–M75 converts the M65 pre-demo research architecture into a narrowly controlled **DEMO-only execution engineering stack**. It does not certify profitability and it does not authorize live-money trading.

The phase is built around one governing rule:

> The strategy Dusty researches, the strategy it simulates, the strategy MT5 validates, and the strategy a Demo Desk proposes must have one semantic source of truth. Execution may measure broker reality; it may not reinterpret the strategy or enlarge risk.

## Authority boundary

Through M75:

- models/news/LLMs cannot send orders;
- StrategySpecV2 cannot bypass capital/risk governance;
- only `DemoMT5ExecutionAdapter` owns the Python `order_send` call;
- the adapter requires a passed immutable `OrderIntent` and fresh DEMO identity verification;
- a latched session can never regain authority;
- `live_write_authorized` is always false;
- a passing M75 software certification framework is not evidence that six real demo desks have already passed.

Operational M75 certification requires external evidence generated on the user's Windows/MT5 environment.

## M66 — Unified Strategy Runtime & PIT Knowledge

Implemented in:

- `src/dusty/runtime.py`
- `src/dusty/pit_memory.py`

### Executable strategy semantics

M58 allowed a rich declarative StrategySpecV2, including source-derived descriptive exit rules. M66 adds an explicit promotion boundary: source prose remains useful research provenance, but executable behavior must compile into a small typed DSL.

Supported executable price-rule classes are intentionally narrow:

- `pct:<fraction>`
- `price:<absolute-price>`
- `atr:<multiple>`
- targets may additionally use `rr:<risk-multiple>`
- breakeven uses `rr:<risk-multiple>`
- `off` is allowed only where absence is safe.

Unsupported or ambiguous strings raise rather than being guessed.

`CompiledStrategy` owns:

- entry-group evaluation;
- session filtering;
- event blocking;
- initial stop calculation;
- initial target calculation;
- trailing/breakeven tightening.

`generate_runtime_trades()` provides deterministic single-position reference semantics. If a coarse bar touches both stop and target, stop wins. This is deliberately conservative and removes hidden optimistic ordering.

### PIT storage

`SQLitePITKnowledge` stores `known_at`, `effective_at`, and optional expiry as absolute epoch instants. `retrieve_as_of()` filters in SQLite itself, so future-known records cannot be retrieved merely because an adapter forgot a second-stage filter. Epoch storage also prevents ISO-string ordering errors across timezone offsets.

### Hard gate

No executable strategy may rely on an opaque free-form exit interpretation, and PIT knowledge unavailable at time T cannot be retrieved at T.

## M67 — Broker-Native Economics & MT5 Trade-Parity Laboratory

Implemented in:

- `src/dusty/broker_research.py`
- `mt5/DustyResearchEA.mq5`

### Broker-native research calculations

`MT5ResearchCalculator` exposes only read/calculation operations. It uses MetaTrader's current account environment to estimate:

- loss at stop via `order_calc_profit()`;
- required margin via `order_calc_margin()`.

It exposes no `order_send` method.

### One strategy interpreter, not two

Rather than reimplementing every StrategySpecV2 feature and indicator in MQL5, Dusty's Python runtime emits a deterministic execution manifest. `DustyResearchEA.mq5` consumes that manifest inside Strategy Tester.

This division is deliberate:

```text
StrategySpecV2
     |
     v
Python typed runtime       <- semantic authority
     |
     v
precomputed tester manifest
     |
     v
DustyResearchEA            <- MT5 execution-mechanics laboratory
     |
     v
normalized MT5 deal ledger
     |
     v
Python parity/reconciliation
```

The EA hard-fails `OnInit()` unless `MQL_TESTER` is true, so it cannot be attached as a normal-terminal trading EA. It uses ticket-specific position closes and exports normalized deal evidence including position ID, deal ID, millisecond time, deal type/entry type, volume, price, commission, swap, profit, reason, and comment.

Cloud CI statically checks the research-only contract and tests manifest/deal parsers. The actual `.mq5` compilation and real-tick tester parity must still be performed on a local MetaTrader 5 installation before operational certification.

### Hard gate

Python strategy meaning remains singular. MT5 supplies independent execution evidence, not a second strategy definition.

## M68 — Empirical Quant Portfolio Risk Model

Implemented in `src/dusty/portfolio_model.py`.

M63 already had a bounded allocator. M68 begins making the Quant PM empirical rather than expecting every dependence estimate from a caller.

The model derives point-in-time:

- strategy volatility;
- paired strategy correlations;
- explicit estimate sufficiency state;
- obvious signed FX currency factors.

For example:

```text
long EURUSD -> EUR + / USD -
long GBPUSD -> GBP + / USD -
```

Sparse history does not become artificial diversification. Insufficient correlation defaults conservatively to high dependence, and insufficient/degenerate volatility uses a conservative fallback. Duplicate returns for the same strategy/timestamp are rejected instead of silently overwritten.

### Hard gate

Unknown dependence cannot be treated as zero dependence merely to allocate more capital.

## M69 — Capital Attribution & Growth Intelligence v2

Implemented in `src/dusty/capital_attribution.py`.

M69 adds append-only economic memory by:

- strategy;
- symbol;
- regime;
- session;
- event class;
- broker;
- PnL;
- capital at risk;
- drawdown;
- governance compliance.

`CapitalReputation` is deliberately lexicographic. Governance pass rate outranks raw return. Only after governance does ranking consider compounded return-on-risk, drawdown and mean risk efficiency.

Consequences:

- a large BAD WIN cannot outrank a smaller GOOD WIN merely because dollars were larger;
- a GOOD LOSS remains a valid observation;
- a loss increases investigation priority, never future recovery size;
- bad outcomes remain durably visible in SQLite rather than being overwritten by later wins.

### Hard gate

Reward cannot teach Dusty that violating the Constitution is profitable behavior worth repeating.

## M70 — Demo Environment Identity & Latched Session

Implemented in `src/dusty/demo_session.py`.

`SessionIdentity` binds execution authority to:

- terminal path;
- terminal build;
- broker/server;
- login;
- account mode;
- account currency;
- leverage;
- account trade permission;
- expert/algo trade permission;
- margin mode;
- broker symbol-spec fingerprint.

A `DemoSession` can only be constructed from an explicitly verified DEMO account with required permissions.

The following faults latch permanently for the session object:

- terminal/build drift;
- account/server/currency drift;
- DEMO→CONTEST/REAL/UNKNOWN mode drift;
- permission loss;
- symbol-specification drift.

Once latched, later normal observations do not restore write authority. Recovery requires construction and complete verification of a new session.

`MT5IdentityProbe.read_connected()` allows identity to be checked on the exact initialized MT5 connection used by preflight/send, reducing time-of-check/time-of-use gaps.

### Hard gate

No session that has ever observed a critical identity/permission drift may regain authority.

## M71 — Immutable Order Intent & Broker Preflight

Implemented in `src/dusty/order_intent.py`.

`OrderIntent` is an immutable, hash-addressed authorization object carrying:

- strategy hash;
- session fingerprint;
- symbol and direction;
- volume;
- reference price;
- initial stop and optional target;
- approved risk fraction and allowed loss;
- PM approval;
- Growth deployment multiplier;
- Risk approval;
- Guardian approval;
- creation/expiry times;
- fill mode;
- magic number;
- price-drift tolerance.

Long and short stop/target geometry is validated at object construction.

`MT5PreflightAdapter` has no send surface. Before it can return a passed preflight it verifies, on one initialized connection:

1. intent/session identity;
2. expiry;
3. upstream governance approvals;
4. current DEMO session identity;
5. current broker tick;
6. acceptable price drift;
7. broker-native loss at stop;
8. broker-native required margin;
9. allowed-loss budget;
10. `order_check()`.

A successful broker preflight is still not treated as proof of eventual execution.

### Hard gate

A changed session, expired intent, excessive price drift, broker loss beyond budget, or failed governance/preflight produces zero broker sends.

## M72 — Demo-Only MT5 Execution Adapter

Implemented in `src/dusty/demo_execution.py`.

`DemoMT5ExecutionAdapter` is the only Python module in this phase that owns `order_send()`.

Immediately before send it:

- requires a previously passed M71 preflight;
- rechecks expiry and session binding;
- initializes the exact terminal;
- re-verifies current identity on that same connection;
- confirms the session is still write-authorized;
- durably authorizes/reserves the intent in the execution ledger;
- only then calls `order_send()`.

Its `live_write_authorized` property is permanently false.

Broker return codes map into explicit lifecycle states rather than assuming a request equals a fill.

### Hard gate

News/model/LLM output can never be passed directly to this adapter. It only accepts the already governed broker preflight object.

## M73 — Order / Deal / Position Lifecycle & Protection

Implemented in `src/dusty/execution_lifecycle.py`.

The durable state machine is:

```text
AUTHORIZED
  -> SENT_UNKNOWN
       -> ACCEPTED / PARTIAL / FILLED / REJECTED / FAULT
            -> PROTECTED / CLOSING / CLOSED / FAULT
```

`SENT_UNKNOWN` is written **before** the broker call. Therefore a process crash after broker acceptance but before local receipt does not create a resendable intent.

On restart:

- zero matching broker observations leaves the intent `SENT_UNKNOWN` for another reconciliation pass;
- exactly one matching broker observation repairs state from the broker order/deal/position evidence;
- multiple conflicting matches fault closed;
- the unique intent/client tag prevents ordinary replay.

Position protection explicitly treats a missing stop as unsafe. Closing requests target the actual position ticket instead of assuming an opposite order will close a hedging position.

### Hard gate

Ambiguous broker outcomes are reconciled, never guessed and never blindly retried.

## M74 — Multi-Terminal Demo Desk & Capital-Compression Supervisor

Implemented in `src/dusty/demo_supervisor.py`.

The execution-aware priority hierarchy is:

1. emergency;
2. open-position supervision;
3. broker reconciliation;
4. journal;
5. evidence;
6. forecast;
7. research;
8. backtest;
9. training.

As resource pressure rises, low-priority work yields first. Even RED pressure still admits position supervision and broker reconciliation.

`SQLiteSupervisorState` provides:

- durable terminal leases;
- atomic conditional lease acquisition;
- same-owner renewal;
- expired-lease takeover;
- release by owner;
- completed-step checkpoints bound to deterministic payload hashes.

This prevents two desk processes from legitimately owning one terminal at the same time.

Capital-compression cycles preserve M64 semantics:

- a failed cycle repeats its existing starting-capital level;
- only a passing cycle may move down to a proposed lower capital level;
- risk percentage is never increased to compensate for less capital;
- zero feasible strategies is a valid safe result.

### Hard gate

Open broker exposure always outranks background research compute.

## M75 — Six-Desk Chaos & Demo Certification

Implemented in `src/dusty/demo_certification.py` and phase tests.

The certification schema requires evidence for M66–M74 bound to one commit by:

- artifact hash;
- data fingerprint;
- configuration fingerprint;
- test fingerprint;
- commit SHA.

The required chaos vocabulary includes:

- network disconnect;
- terminal restart;
- process restart;
- login drift;
- DEMO→LIVE drift;
- permission loss;
- spread/slippage spikes;
- order rejection;
- partial fill;
- duplicate response;
- missing response;
- manual position;
- stop-protection failure;
- low disk/high memory;
- backtest overload;
- stale market data;
- clock anomaly;
- capital infeasibility.

Certification fails if:

- any required milestone evidence is absent/failing/mismatched to the current commit;
- any required chaos case is absent or fails;
- a chaos run records an unauthorized entry attempt;
- desk-run identities are duplicated;
- any supplied desk run fails;
- fewer than six desk runs pass.

Hardware does not need to run all six desks simultaneously. Sequential desk runs may count when each run is independently bound to its own session/ledger/cycle evidence.

Even a fully passing bundle returns:

```text
demo_desk_certified = True
live_write_authorized = False
```

### Critical distinction

The repository now contains the **certification machinery and deterministic fault contracts**. It has not, by virtue of cloud CI, completed six real broker-connected demo desk runs. Real M75 operational certification must be performed locally against the user's MT5 demo environment and its generated artifacts.

# Reference-repository audit applied to M66–M75

Dusty adopts concepts, not framework dependency trees.

| Reference | Current lesson retained | Applied in Dusty | Explicitly rejected / bounded |
|---|---|---|---|
| Kronos | Financial K-line specialist; probabilistic samples | optional forecast evidence later | never execution authority; project examples themselves caution against production interpretation |
| Chronos-2 | zero-shot uni/multivariate/covariate forecasts; quantiles | future probabilistic challenger/scoring | no direct broker authority |
| Uni2TS / Moirai | rolling evaluation; probabilistic metrics such as CRPS/MASE | reinforces OOS/scoring architecture | no framework dependency in core |
| Vibe-Trading | exact symbols/units, warm-up isolation, fail-closed broker reads, durable pre-send ownership, exact client IDs, no resend after lost response, kill-switch durability | M57/M59/M67/M70–M74 | do not copy the broad agent/runtime dependency graph |
| Microsoft Qlib | loose coupling across data, models, strategies, portfolio, execution; PIT database concepts | phase separation and independent laboratories | no need to import Qlib runtime |
| Microsoft RD-Agent | research idea → implementation → quantitative validation → feedback | Dusty's learning loop | research agent cannot modify execution constitution |
| TradingAgents | role decomposition; PIT fixes; durable decision/checkpoint memory | cautionary evidence for time-correct memory and restart semantics | LLM debate does not vote a trade into existence |
| ai-hedge-fund | persistent fund/mandate separated from ticker universe; pluggable alpha models | desk/mandate thinking and frozen strategy identity | proof-of-concept trading claims are not evidence |
| Automaton | SQLite state, heartbeat/resource tiers, immutable laws, audit/versioning | M74 state/resource patterns | self-funding, wallets, replication, survival pressure, sovereign self-modification |
| Microsoft Agent Framework | graph fingerprint, checkpoint ancestry, committed-only state, atomic checkpoint writes | durable checkpoint design genetics | framework runtime not required for Dusty's small deterministic state machine |

## The strongest external confirmations this phase

Vibe-Trading's late-August 2026 fixes are particularly relevant because they independently encountered failure classes Dusty is defending against:

- wrong symbol resolution;
- asset-unit/currency distortions;
- warm-up rows contaminating performance;
- fail-open broker error envelopes;
- restart-induced duplicate flattening;
- ambiguous live send recovery;
- exact client-order identity;
- durable kill-switch episodes.

TradingAgents' 2026 PIT/checkpoint fixes reinforce that persistence alone is insufficient: stored memories and resumed state must also respect historical knowledge time and the actual workflow shape.

Microsoft Agent Framework reinforces that durable checkpoints should bind to topology/signature, preserve lineage, and contain committed state rather than arbitrary pending mutations.

# CI versus operational certification

GitHub Actions can certify deterministic code contracts on Windows and Ubuntu:

- Python compilation;
- unit/invariant tests;
- injected MT5 boundary behavior;
- deterministic replay/idempotency logic;
- static tester-only MQL5 safety contract.

It cannot certify:

- local MetaTrader build compatibility of the `.mq5` file;
- a broker's actual symbol/filling/account behavior;
- real-tick Strategy Tester parity;
- real demo order/deal/position behavior;
- network/terminal fault recovery on the user's PC;
- six actual desk runs.

Those artifacts must be generated during local integration and then supplied to M75 certification.

The distinction is intentional: **software readiness is not broker-environment certification, and broker-environment certification is not profitability certification.**
